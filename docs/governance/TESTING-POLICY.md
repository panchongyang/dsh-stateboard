# 分级测试与基线保护规范

> **强制底线：高风险变更不得在基线上直接修改，也不得直接在基线上试测。先独立变更分支/worktree和隔离测试，再人工验收；通过后才讨论合入与部署。**

- 分级测试与基线保护是用户要求的固定流程。
- 独立测试站点使用单独的登录。参考环境的验收范围只覆盖对应的候选、环境和业务流程。
- 适用对象：人、主控 agent、子代理，及其直接/间接调用的脚本；风险按行为和影响面判断，不能按文件扩展名判断。
- 操作手册：[TEST-ENV.md](<TEST-ENV.md>)。本文件规定“什么条件下可以测/合入”，手册规定“如何启动/打开/停止测试环境”。

## 1. 基线、候选与环境

**受保护基线**包括：稳定分支/工作树（当前 master）、日常部署版本/主 DSH、真实工作区及其配置/会话/存储/密钥，也包括已确认的参考版本及其验收数据。不能把“目前在开发分支”理解为可以不断覆盖已验收参考版本。

**候选**是从明确基线提交派生、为一次变更单独登记的分支/提交。已通过的候选一旦修改，原通过结论不能自动覆盖新内容。

1. 开发默认在变更分支，不在 master 或日常部署目录写代码。R3 必须有**专用变更分支 + 独立 worktree**；既有已验收参考工作树保持不动，不拿它当高风险施工现场。
2. 测试必须使用该候选的独立进程、home、agents、workspace、board/执行密钥、日志与认证。**只换端口/profile或只切工作区不算隔离。**
3. 测试站点使用独立端口、Cookie 和登录。每个候选工作树使用自己的测试根。端口冲突时选择空闲端口，保留已有服务的配置与进程。
4. 默认使用合成 fixture。需要真实数据对照时，先获用户明确授权，做一致性导出/脱敏副本，放进专用测试目录；不直接挂真实 store，不复制整份真实 home、凭据或生产执行密钥。
5. 需要旧版本对照，也从该版本创建**另一个隔离参考 worktree/数据副本**运行。不得为了复现旧 bug 就在稳定基线上运行故障、损坏或副作用探针。
6. 基线仅做必要的版本/配置/哈希等只读核对；发布后的非破坏冒烟不能变成研发试错。高风险代码与测试目标不得指向基线目录、真实项目数据或主实例。

## 2. 风险分级（混合改动取最高级）

| 级别 | 典型变更 | 最低验证与准入 |
|---|---|---|
| **R0 · 纯文档** | 文字、链接、格式；不改变执行行为或安全边界 | 文档/链接/命令存在性核对、`git diff --check`、确认仅文档差异；不为文档更新重启服务或跑有副作用命令 |
| **R1 · 低风险局部** | 可证明不改变契约的局部整理、非关键纯函数、展示文案/样式 | 独立分支；相关单测与静态门禁；前端变化显式构建并核对产物，在隔离实例人工点检受影响位置 |
| **R2 · 使用流程/集成** | 用户交互流程、跨模块功能、工具/HTTP接口、外部调用或一般行为变化（未触发R3项） | R1 + 完整自动门禁、真实隔离实例HTTP/资源核对、受影响流程人工验收；有写入则验证失败无副作用、刷新/重启持久化 |
| **R3 · 高风险** | 状态机/任务迁移、租约/fencing/intent/锁、事件/日志/快照/回放/迁移/恢复、验收/证据/签名、人审/角色/认证/权限、共享依赖/生产插件装配、部署/默认policy、文件删除/重置/路径搬迁/进程终止 | R2 + **专用变更分支/worktree、事前风险与回退方案、针对性异常/并发/兼容性及恢复验证、独立审查、用户明确验收**；不得在基线上直接改或直接测 |

升级规则：
- 按影响取最高级；不确定至少按 R2。涉及持久数据、授权边界、共享运行时或潜在破坏性操作，按 R3。
- “只有一行”“只是脚本/配置”“只是重构”“先试一下”“有备份”均不能降级。文档若改变运维执行步骤或安全边界，步骤本身按对应风险评审；执行时仍按 R3 管控。
- R2/R3 的UI展示改动若会触发状态/权限/数据语义，不得按R1样式变更处理。
- 同一提交混入更高风险变更，整份候选升级；拆成真正独立可回滚的提交后才可分别评估。

## 3. 固定流程（先判级，再动手）

### A. 开工登记

任务/intent 中记录：风险级别及理由、基线提交、专用分支/worktree、测试数据/实例范围、预期验证、是否需人审。R3 还须在修改前写清失败影响、代码/数据回退方法及恢复验证。子代理继承相同边界；记录 `delegation: yes|no — reason`。

没有确认这些信息，不开始高风险修改；环境未就绪则先修环境，不能转去基线凑合验证。

### B. 独立实现与自动验证

1. 在候选工作树实现，先加能命中问题的回归（修bug时优先先红后绿）。默认不共享测试运行目录/数据。
2. 按级别执行自动验证。R2/R3 至少完整运行候选已有的 `npm run check:strict` 与 `npm run check:architecture`；接口/宿主变化不能因离线CI通过而省略host回归。
3. 前端有变化时，显式重建并核对对应产物；`env:test:verify`只证明服务产物与当前文件一致，不证明源码已正确重建。
4. 只运行该候选实际提供的脚本。不同分支门禁可能不同，缺失的必要验证必须补齐；不得声称不存在的脚本已通过，也不能到生产上补测。

### C. 冻结候选并核实测试版本

提交候选、确认工作树干净，记录 commit/产物哈希与DSH版本；冻结后复核该候选的必要自动门禁（R3重跑完整门禁），不能只引用提交前脏工作树的通过结果。启动该候选的隔离实例，用 `env:test:status` 核对启动提交，用 `env:test:verify`核对完整BOOT、认证、API、测试数据和前端模块。

测试期间不得边改源码边让用户验收同一个版本。源码、配置、构建产物或关键依赖有任何变化，重新提交、按影响复测，并重新明确候选版本；原验收不自动续用。独立登录仍是必需步骤，不能为了方便关闭鉴权或复制生产Cookie。

### D. 人工验收与R3额外闸门

- 人工验收至少覆盖受影响的正常流程、拒绝/错误提示；涉及持久化则包含刷新与停止/重启后的保留。UI/交互默认由用户手验，不把HTTP通过或自动单测全绿当成UI验收。
- R3 按变更面增加：角色/状态/token/租约/attempt组合，拒绝无日志/文件副作用，双进程竞争，故障点注入，新旧版本回放/兼容分类，恢复及数据回退演练。**不相关项目可标不适用并说明理由，相关关键项不能跳过。**
- 崩溃、杀进程、破坏/截断日志、模拟磁盘失败等仅作用于专用fixture/已授权测试副本；模拟“生产配置”也必须用临时配置，不得拿真实环境当靶子。
- R3 由非实现者做有边界的独立审查。看板普通任务的 Agent 验收不能代替此工程审查；已开审计门仍禁止 worker 自审或关门。新增重闸门/默认policy须说明存量影响，不能悄悄全项目开启。

#### D.1 删除或收窄 API 表面时的额外审查要求

删命令、删参数、删错误码这类"表面收窄"，门禁全绿不代表没退化：它是**连锁删除**，入口背后往往承载隐式能力，而测试常在同一提交里被改写，正好把该能力的断言一并改掉。审查必须做到：

1. **双基线对照**：用 `git archive <父提交>` 与 `git archive <候选提交>` 各导出到系统临时目录，跑**同一场景脚本**，比较行为差异。只跑候选版本看不出的问题，双基线一眼可见。
2. **逐条比对被改写断言的意图**：每个被改写的用例给出改动前后断言原文，说明"原来验证什么、现在验证什么、是否等价"。出现"成功断言变成拒绝断言"必须显式判定，不允许笼统写成"随新入口迁移"。
3. **证明被删入口承载的能力有新去处**：列出该入口支持的每种场景，逐一说明替代路径或"该能力明确消失"的理由。例：删掉人工批准命令时，必须回答"搬迁后如何继续钉版本、如何读取旧证据"。
4. **fixture 里的 bootstrap 辅助会遮蔽首次使用缺口**：形如"先造一条证据再测"的辅助，必须另外证明**首次使用路径**（新项目、从未产生过记录）也可用，否则通过只是绕开了前置条件。
5. **只读能力不得依赖前置状态**：纯读接口（如读取固定内容）不允许以"先写入记录/先批准一次"为条件；审查要单独构造"全新项目 + 只读调用"用例。

上述要求在移除批准入口的改动中验证有效：门禁与全部单测通过、删除清单干净，但"同源重绑定恢复"与"首次只读 bootstrap"两项能力被一并删掉，均由双基线对照发现。

### E. 合入和部署是另两次决定

**环境可用确认 ≠ RFC通过 ≠ 候选功能验收 ≠ 同意合入 ≠ 同意部署。**

测试通过只让任务进入 review；保留人审。用户明确同意对应候选后，才按授权合入；部署还需单独确认目标、时间/影响范围、代码与数据回退点，再按发布流程执行。没有明确授权，不改生产插件路径、不把主服务指向开发工作树、不重启主DSH。

一个合入/发布应是可独立回滚的语义变更。涉及事件/存储必须声明兼容性；新数据旧代码不可读时，不能只切回代码就宣布回滚成功，必须说明数据快照及允许的数据损失/RPO。合入解决冲突或产生新内容后，以实际集成候选重新跑相关门禁，不沿用冲突前的结论。

## 4. 失败处置与禁止事项

- 任何相关门禁失败：留证、停止晋级，回候选分支修复；不得临时切基线热修、在主实例重跑探针或关闭审计来求绿。
- 实例/数据路径/版本不符：立即停止本次试验，先核对归属；不得继续写入后再解释环境。
- 不自动删除锁、猜测接管或按磁盘旧PID强杀；控制端点失联/stale时先人工确认。独立实例不是 OS 沙箱，不能以“这是测试环境”推导它能隔离OS权限。
- 备份不是直接在基线试错的许可。不得用真实项目跑破坏性回归、迁移试验、证据命令重跑或故障注入。
- 不把分级规范描述成已经实现的自动拦截器：当前是执行约束与验收清单；未来若做脚本强制门禁，另立任务并按R3验证。

## 5. 可执行测试分层、规模与覆盖率

- [Suite manifest](<../../test/suite-manifest.mjs>)是 runner、discovery、coverage 的单一接线来源；每个 tracked `.test.mjs` 恰属一个叶 suite，显式路径排除未跟踪测试。详见[测试索引](<../../test/README.md>)。
- `test:core` 为规模门禁 + unit/integration/cli/ops；层间串行、层内文件并发上限 4，wall-clock 预算分别 480/480/300/300 秒。host 独立（300 秒，不进入离线 CI）；perf/recovery 分别 300 秒且不在 core/fast。runner 输出实际耗时和预算，超时回收本次子进程树、非零退出。
- `check:strict` 依次执行 audit:check、npm test（core + host）、perf、recovery、stores gate、release；失败即停。CI 执行离线 core（含全部 client 且不重复）与独立 perf/recovery，不以缺 peer 的离线结果代替完整宿主验证。
- [规模门禁](<../../scripts/check-test-size.mjs>)对 tracked `test/**/*.test.mjs` 采用物理行计数（含注释/空行）：新文件 ≤600，函数 AST 行 ≤150（包括匿名回调，无函数例外）。四个精确既有 ceiling 是 [bundle-logic](<../../test/client/unit/bundle-logic.test.mjs>) 781、[external-docs](<../../test/client/unit/external-docs.test.mjs>) 607、[logic](<../../test/client/unit/logic.test.mjs>) 883、[evidence-audit](<../../test/docs/evidence-audit.test.mjs>) 860；任何增长即失败，不自动更新，≤600 后必须移除 stale exception。既有超限须按职责另行拆分，不借例外新增大文件。
- `test:coverage` 覆盖 manifest 全部 wired tracked 入口（含 client/unit、host preflight、perf/recovery），预算 1800 秒；Node V8 line/branch/functions 阈值分别 90/80/90%，任何不足非零退出。分母保留 Node 默认 loaded-project JS（产品与维护脚本，默认排除测试文件和 node_modules，路径以报告为准），不是产品源码独立覆盖率。报告逐文件数据，手工 worker 与动态 bundle 的采集边界单列，不能用高总百分比遮蔽未执行能力。
- TAP 输出 skipped 数与用例名。SKIP 回调未执行、不贡献覆盖；缺 peer、平台能力或真实 store 未授权须单独列明。real-store opt-in 跳过保留，SKIP 不能算真实数据覆盖，coverage 也不授予真实数据访问权。

## 6. 每次交付的最小留证模板

```text
任务 / 日期 / 实现者 / 独立审查者：
风险级别及理由（混合取最高）：
基线commit / 候选分支 / worktree / 候选commit：
DSH版本 / 产物hash / 配置或依赖变化：
测试实例地址 / home、workspace、board范围（不得记录token/密钥）：
数据来源：合成fixture / 经谁授权的脱敏一致性副本：
命令与结果：pass/fail/skip；必要但未覆盖的项和原因：
R3异常/并发/兼容/恢复项目：结果 / 有理由的不适用项：
用户人工步骤、预期、实际、确认人和确认的候选版本：
基线未修改/未用于试测的核对证据：
已知限制 / 代码回退点 / 数据快照与RPO / 恢复验证：
用户合入授权：未获准 / 已确认对应commit：
用户部署授权：未获准 / 目标与影响范围：
delegation: yes|no — reason
```

报告只列实际执行结果；不得把之前版本的测试数字、人审记录或环境验收套到新候选。授权记录留在任务/项目文档中，不能仅靠会话记忆。
