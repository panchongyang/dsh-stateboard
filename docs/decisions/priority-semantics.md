# 决策：优先级语义与可视化口径

> 状态：已替代（现行语义见[实现契约](<../CONTRACT.md>)；正文保留方案或决策时的语境）。

> 2026-10-22 · 影响 P5（排序/rank/「下一个」）与 P6（徽章落地）· 不改 core

## 1. 现状（为什么"看不清优先级区别"）

- 排序其实已经存在：`lib/core/views.js:5` 按 `priority` 升序、同值按 `updatedAt`。所以列的次序是对的。
- 但界面上只有一个 **10px、中性灰、等宽的 mono badge「P150」**：没有名次、没有排序控件、跨列无法比较。看板上「P150」和「P320」长得一模一样，用户只能自己去比数字大小 —— 这就是看不清的原因。
- 语义还有一层反直觉：**数字越小越优先**，且 `100` 是"未显式设定"的默认值（本项目 6 个 done 任务都是 P100）。

## 2. 被否决的方案：阈值分档着色

"≤150 紧急 / 151–200 高 / 201–250 中 / ≥251 低"看起来直观，但有两个硬缺点：

1. **默认值会被误判**：P100 是"没设"，套这个阈值就是"最紧急"，本项目的历史任务会整片变红。
2. **阈值是今天的快照**：项目规模或习惯一变（比如都改到 200 以下），档位就失真，还得再改代码。

## 3. 采用：位置编码优先，颜色只做强调

1. **rank（唯一真源）**：`priorityRanks(tasks)` 按 `(priority asc, updatedAt asc)` 给**活跃任务**（backlog/ready/in_progress/review/blocked/interrupted）编号 `#1..#n`。
   - **done / canceled 不参与编号**（否则完成的任务会占住前几名）。
   - 纯函数，列表、看板、抽屉三处共用，禁止第二套实现。
2. **位置**：列表视图按 rank 排；看板列内同序（列内天然有序，不显示第二个数字）。
3. **强调**：rank 1–3 用 accent 左边条 + 加粗序号；其余用 `--pb-text-3`。**只强调前三名**，不做五档配色。
4. **「下一个」**：页头固定一条 `#1 · P150 · UI 2.0 · P1 排版与控件基线`，点击直接开抽屉。这是"看不清"最直接的答案：不用比较，直接看一条。
5. **原始 P 值**：保留（等宽数字 + 抽屉里显示），但**不放大、不配色**——它是机器刻度（100 步进，跨度 100–320），对人类不是可读量纲。hover 提示「数字越小越优先；100 = 未设定」。
6. **排序控件**：列表视图提供「优先级 / 最近更新」；切换只改**渲染顺序**，不改 rank 值。看板列内恒按优先级，列头标「按优先级」。

## 4. 验收口径

- 同一任务在列表 / 看板 / 抽屉里 rank 一致。
- rank 1–3 在两视图中的强调样式一致（同一 class）。
- 切换排序不改 rank（有单测：同 priority 时按 updatedAt 决定次序；done/canceled 不参与）。
- 徽章与「下一个」条的 tier/rank 全部来自同一个函数（无第二套阈值）。

## 5. 影响面

- **P5**：`priorityRanks()` + 列表排序 + 「下一个」条 + 视图切换。
- **P6**：卡片徽章用 P5 的同一函数渲染。
- **core / HTTP / 数据格式**：不动（priority 数值语义保持原样）。
