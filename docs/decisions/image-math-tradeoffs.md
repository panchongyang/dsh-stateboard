# 图片与数学公式：做不做（文档渲染 · 阶段6）

## 结论

| 能力 | 本轮 | 理由 |
|---|---|---|
| 图片 | **不做**，保留链接语义 | 需要资产上传 + host 静态路由 + 存储清理，是一次契约级扩展 |
| 数学公式 | **不做**，不引 KaTeX | 体积 + 与「禁 innerHTML」契约冲突 |

两者都写成「明确不支持」：Markdown 里的 `![alt](url)` 会按普通链接显示（保留可点的 url），`$…$` 原样显示为文本。

## 图片：为什么不做

要真正显示图片，缺的不是渲染，是**资产管线**：

1. **上传端点**：`POST /projects/:id/assets`（multipart 或 base64）、大小上限、MIME 白名单、sha256 去重。
2. **host 静态路由**：`GET /projects/:id/assets/:assetId`，带缓存头；还要考虑 DSH 的 authority/cookie 与局域网访问。
3. **存储与清理**：资产落在哪（项目目录？tmp？）、删除文档时是否 GC、备份/迁移是否带上。
4. **契约变更**：新事件（`asset/added`）、新命令、fsck 规则、`CONTRACT.md` 与 `API_PATHS` 冻结表都要改，属于 `v1.0 → v1.1`。

代价估：一个 host 子系统 + 契约改动 + 迁移与回归，量级大于本阶段其它三项之和。
收益：文档能贴截图。

**替代**：现在写 `[截图](file:///D:/...)` 或外部 https 链接即可，正文里保留路径文本。

**重估触发**：连续出现 ≥3 次「文档必须带图」的真实需求，或项目开始承载对外文档。

## 数学公式：为什么不做

- **体积**：KaTeX 的 JS + 字体约 1 MB，占当前客户端 bundle（约 270 KB）的四倍；这会直接违背「客户端只有一个小 bundle、只 require react」的既定约束。
- **契约冲突**：KaTeX 的输出是 HTML 字符串，必须 `dangerouslySetInnerHTML`，而客户端有一条硬约束测试「禁止 innerHTML / dangerouslySetInnerHTML」。要走 MathML 的话，Chromium 的 MathML Core 只覆盖一部分，Firefox/Safari 表现不同，排版质量明显下降。
- **收益**：项目文档里公式出现频率低。

**替代**：用行内 code 或代码块写 LaTeX 原文；需要渲染时外部工具转图片再走链接。

**重估触发**：出现需要展示 ≥10 个公式的文档，或用户明确要求。

## 影响

- 渲染器行为：`![](...)` 显示为链接（`!` + 链接文字），`$x^2$` 显示为纯文本；不报错、不吞内容。
- 本决策的变更需要新任务，并修订本文（`decision` 类型，保留历史修订）。
