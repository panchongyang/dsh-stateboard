# 任务 worktree、Git 隔离与串行集成

## 状态与范围

配套草稿计划：多会话并发推进：计划任务解耦、worktree 隔离与串行集成（内部草稿，未发布）。本文为待实施设计，不表示已有 worktree 管理器、Git 强制隔离或多工作区绑定。当前只整理文档，不创建分支/worktree，不运行 Git、测试或服务。

共同设计依据见[《设计草案：多会话并发推进与计划—任务一致性》](./multi-session-concurrency.md)；分期和验收见[《实施与验收草案：并发推进分期、依赖及 R3 门禁》](../specs/concurrency-phases-acceptance.md)。

## 1. 隔离单位

每个并发开发任务/执行尝试有独立 worktree 和任务分支。按任务分，不按计划分：同计划的两个并行任务也不得共用工作目录或暂存区。一个 worktree 同时最多供一个有效执行使用。

```text
同一仓库（公共对象库与 refs）
├─ 任务 A worktree + 任务 A 分支 → worker A
├─ 任务 B worktree + 任务 B 分支 → worker B
└─ 专属集成 worktree + 集成候选分支 → 单一集成者
```

worktree 隔离工作目录、index 和 HEAD，不消除共享 refs/stash/config/部分维护状态，也不消除合并时的代码或业务冲突。Git 自身的锁保护命令内部元数据，不覆盖整个“修改→测试→提交”过程。仅给 Git 命令排队或仅创建不同分支而共用目录，都不是足够的执行隔离。

worktree 不是 OS 沙箱；可信 agent 仍可能通过通用 shell 写到别处。首期的受控工具与协议用于防误操作，不能宣称已阻止所有任意命令越界。强对抗隔离需账户、容器或 OS 权限等另一层边界，不在本期承诺内。

## 2. 项目身份与执行绑定

项目身份不随任务目录改变。目标映射为：

```text
projectId + repoId
  → taskId + attempt/intentId + taskDefinitionVersion
  → sessionId + sessionEpoch + leaseToken
  → canonicalWorktreePath + branch + baseCommit
```

建议执行记录还包含生命周期状态、创建/最后确认时间、候选 commit、集成目标、资源分配和失败/清理原因。具体字段和事件版本由契约任务冻结。

- repoId 应由登记的仓库身份/公共 Git 目录等可核验事实确认，不能只凭远端 URL、目录前缀或分支名认领。
- worktree 路径需规范化并验证确属登记仓库和允许工作区；Windows 大小写、路径别名、兄弟目录、junction/symlink 不能造成重复绑定或越界。
- 一个项目可登记多个执行工作区。原主 workspacePath 保持兼容；不因新 worktree 的 cwd 自动创建另一块项目板。
- session 显式绑定 projectId 和执行工作区，服务端校验 actor、session epoch、租约、taskId 与仓库身份；不能把调用方提供的 projectId 当授权证明，也不能悄悄回落到另一个项目。
- fork/新会话不继承父执行权。绑定移动、重新 attach、租约失效或重启恢复都需要验证/撤销相应执行权，不复用旧 token。
- 会话 cwd、命令实际 cwd、证据根目录应一致指向获准的任务工作区；UI 的祖先目录便利匹配不能充当宿主执行授权。

## 3. 生命周期与失败处理

目标流程：用户批准发布与实施 → claim → begin 写明准备工作区等预期副作用 → 校验绑定/预算 → 创建专属 worktree/分支 → 开发测试 → 冻结候选 commit → 提交候选证据 → 审阅/集成 → 显式保留或回收。

创建/登记须具备幂等性与补偿记录。创建成功但登记/响应失败、目录已存在、分支已被占用等情况，先诊断并核对身份，不能覆盖、硬重置或删除未知目录。对同一任务重复请求不再分配第二个活动 worktree。

进程重启、失联、拒绝、interrupt 或 fencing 失效时，执行记录进入待 reconcile 状态。存在目录、commit 或后台进程不等于任务完成，也不等于允许新 owner 沿用旧环境。旧 worker 丢失执行权后须停止后续动作；已经发生的副作用与未能阻止的在途命令须明确登记，不能把 token 误当作可撤销任意 OS 写入的锁。

回收前必须确认：无有效 owner/租约，无未结清 intent 和未知在途执行，工作树无未保存成果，提交已按保留策略保存或用户明确同意放弃，目录身份与绝对路径正确。拒绝自动强制删除脏 worktree、分支、残留锁或未知进程；保留检查和显式回收入口。

## 4. Git 操作边界

| 操作者 | 允许范围 | 首期限制 |
|---|---|---|
| 任务 worker | 在自己的 worktree 检查 diff/status、修改、测试、add、提交任务分支 | 不操作其他工作树，不修改受保护/集成分支，不使用共享 stash，不更改公共 config，不自行 prune/gc/强制删分支或 force-push |
| 工作区管理器 | 校验身份后创建、登记、诊断和显式回收专属工作区 | 仓库级分配/回收操作协调，失败可恢复；不手工删除 Git 锁来抢占 |
| 集成者 | 在专属集成工作区按队列合入任务 commit、解决冲突、验证集成候选 | 单一集成队列；不在 worker 工作区切分支、reset、stash 或清理 |

自己的工作区内涉及 reset/clean/丢弃未提交成果也属于破坏性操作，需按风险及授权处置，不能仅因“是自己的目录”就自动允许。原生 Git 可以安全处理的不同任务分支提交不额外套全仓库长锁，避免重新把开发过程串行化。

## 5. 串行集成与完成语义

- 任务候选固定 baseCommit、headCommit、定义版本和验证记录；提交后继续修改须形成新候选并重新验证，不能验收一个 hash 后合入另一个未验证版本。
- 集成者按依赖/队列在最新集成基线上 cherry-pick 或 merge；遇冲突停止该项，明确由谁修复，不静默修改别人的工作。
- 每次集成后重新验证受影响组合。A、B 分支各自通过不推出 A+B 一定通过。
- 开发任务完成的定义必须在契约中二选一定义清楚：若完成表示“候选验证通过”，则另设集成/整体交付任务，依赖最终交付的任务必须依赖该集成结果；若完成要求“已集成”，则在集成前不得标 done。不得把候选提交当作最终交付。
- 集成、用户验收、合入受保护主线、部署是不同门，不能由一次 submit 或一次测试通过全部放行。部署和本机 DSH 重启不自动执行。

## 6. 执行、证据与运行时资源

- 宿主 command/test 的 cwd、file 相对路径、产物收集和 hash 审计使用绑定的执行根，而不是共享项目主目录；拒绝路径逃逸与跨任务取证。
- 证据关联 task/attempt/intent/token、任务定义和候选 commit。文件漂移按该候选口径审计；集成候选另有自己的证据，不覆盖原任务历史。
- 变更 execution 签名/凭证字段时保持版本化兼容，旧数据不得无条件当作新强证据，也不得因新增字段把既有合法记录全部破坏。保留 preflight、真实提交校验和人审规则。
- preflight 无法撤回校验后已开始的任意命令；提交 stale/执行中失权等窗口必须有副作用记录及 reconcile 路径，不能承诺物理 exactly-once。
- 每任务独立输出目录、临时目录、缓存写入和必要的日志；端口、数据库/命名空间、外部服务和部署目标用显式资源配额/互斥键约束。
- 多个 worktree 不默认共享可写依赖安装目录；node_modules、构建工具缓存、包锁及 hooks 的行为需要验证或隔离，避免候选相互污染。
- 本机稳定 DSH、真实 home/agents/store/认证、生产凭据和受保护工作树不作为试验对象。测试使用独立候选、合成 fixture 和隔离环境；不把“换端口”称作完整隔离。

## 7. 最小验收场景

1. 两个任务分支并发 add/commit，只包含各自内容，互不改变另一方 HEAD/index/工作目录。
2. 同计划两任务、跨计划两任务均可绑定到同一个 projectId 的不同工作区；错仓库、错 session、重复占用、跨任务路径被拒绝。
3. 共享资源冲突返回明确原因，不能只以任务 WIP 有余量就启动。
4. 创建或登记中断、响应丢失、租约失效、重启、脏目录与冲突合入都有可诊断保留路径，不丢成果。
5. 命令 cwd、文件证据和候选 commit 匹配；其他任务改动不造成证据串线。
6. 分支分别通过但集成失败时，最终交付门保持关闭；未授权不得部署或回收工作区。
