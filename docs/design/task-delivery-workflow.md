# 任务确认后的完整工作流

状态：用户已确认的项目工作流框架。默认完成到合入，实施分工、工作树隔离、独立审查和基线同步按本文执行；不替代具体任务的授权、风险验证和安全约束。

定位：描述本项目开发者/AI 的协作流程，不把分支、测试环境或发布编排变成项目板产品职责。依据 [产品方针](<../PRODUCT-PRINCIPLES.md>)、[协作治理指导](<../AUTONOMOUS-DELIVERY.md>) 与 [贡献指南](<../CONTRIBUTING.md>)。

## 1. 总原则

- 人决定做什么、边界和授权；AI 在授权内负责实现、验证、审查及交付，不让用户逐技术步骤审批。
- 工程质量同时包含运行正确性、变更安全性、长期可维护性；不能只以测试全绿作为完成条件。
- 普通技术问题在流程内解决；需求/职责/安全或授权发生变化时，才升级给用户。
- 区分：代码写完、测试通过、独立审查通过、集成完成、目标环境生效、任务验收完成。
- 流程和角色是必要职责，不要求每阶段新建文档、卡片或会话。

## 2. 角色

| 角色 | 负责 | 不负责 |
|---|---|---|
| 用户 | 确认目标、非目标、验收和授权；处理产品取舍与重大例外 | 常规逐文件审查、每轮测试结果签字 |
| 主控/任务负责人 | 确认边界、组织实施与审查、核实产物和证据、控制范围并完成交接 | 只转述子代理“完成”就宣布交付 |
| 实现者 | 设计必要细节、编码、自测、记录失败及修复 | 以自测代替独立验收、擅自扩大职责 |
| 独立审查者 | 核对最终候选的功能正确性、需求一致性、三个产品方针及未覆盖范围 | 只审实现者摘要或用流程通过替代正确性判断 |

### 实施分工

- **多任务卡**：主控组织子代理持续推进，负责依赖、分工、冲突、审查、集成和接续下一张获准任务；不在每张卡完成后例行停下来等用户再次说“继续”。具体串并行和同时领取范围遵守任务状态机与当前执行约束，不等于同时修改重叠代码。
- **单任务、边界清晰且规模可控**：主控直接实现，不为形式额外委派；达到运行时强制委派阈值时按其规则处理。
- 主控承担最终组织和交付责任，子代理完成报告不直接等于任务完成。实现者无论是谁，均不能把自审称作独立审查。
- 普通返工由主控组织完成。只有产品决策、权限例外或真实阻塞需要用户处理时才暂停升级。具体模型、委派粒度和会话数量不在本框架写死。

## 3. 主流程

```text
任务确认
  → 开工准备
  → 实现与局部验证
  → 在自己的开发分支/worktree同步目标基线并解决冲突
  → 完整自验、固定候选
  → 独立审查
  → 确认目标基线未再变化，按授权合入并复核最终产物
  → 提交验收、关闭与交接
```

### 0. 任务确认：建立唯一有效的需求基线

- 明确目标、范围、非目标、验收标准、依赖与风险。
- 挂上已批准方案；简单任务可以直接用卡片表达，不强制补长方案。
- **默认完成终点是合入约定的目标分支**，包括验证最终合入结果；只留候选、分支或补丁不算默认完成。特殊任务另行约定。
- 默认不包含发布、部署、重启或目标环境生效；这些操作单独授权，必要时另卡交接。
- 开工时确认目标分支与执行权限；在有效授权内连续推进，不逐技术阶段请求审批。具体指令限制提交或合入时遵守限制，明确停留环节，不把未合入候选称作已完成。
- **产出**：任务卡 + 必要方案 + 验收与授权边界。

### 1. 开工准备：确认在哪里、基于什么做

- 读取任务最新状态、方案和相关约定，领取任务，副作用前记录执行意图。
- 确认基线、已有改动、并行任务、实现目录与测试数据隔离；不清理或覆盖别人改动。
- 按 [测试分级规范](<../TESTING-POLICY.md>) 判定风险，预先识别可能冲突的文件和接口。
- **预计改动超过3个代码文件（即4个及以上），默认使用独立worktree**；任务中途扩展到这一规模，先迁移到隔离工作树再继续，不等全部改完后补隔离记录。该门槛按代码文件计算，不以文档数量代替。
- **R3无论文件数量多少，都保留专用变更分支与独立worktree要求**。不超过3个代码文件不构成高风险免隔离的理由，也不免除测试数据隔离和并行冲突检查。
- 只澄清会阻断正确实现的问题，不重开已经确认的产品讨论。
- **产出**：简短执行安排，包含基线、负责范围、环境、验证方式和交付位置。

### 2. 实现：小步完成任务，不顺手扩张

- 按批准边界编码，并同步必要的契约、测试、文档和生成产物。
- 先验证局部行为，再扩大到相关调用方、异常路径和生命周期。
- 发现问题先区分：任务内必须修复、独立问题、需求变更。独立问题记录，不默认捆绑。
- **产出**：可运行候选与对应回归，重要取舍和例外有简短记录。

### 3. 同步基线、自验并固定候选：让审查有明确对象

- 集成与交付前，**先在自己的开发分支和worktree中同步约定目标分支的最新基线，冲突也在自己的候选工作树解决**；不切到受保护基线解决冲突、调试或补代码。
- 同步、冲突处理及必要产物重建完成后，再对整合后的候选执行验证、固定身份并交独立审查；记录这次纳入的目标基线提交。
- 同步方式遵守不改写共享历史的约束，不以同步基线为由rebase已共享分支或force push。
- 执行要求的定向、默认及风险相关验证，记录实际命令、结果、失败、跳过和未覆盖。
- 失败必须调查；“基线也失败”“环境问题”“无关”均需证据，不能直接换成通过。
- 核对改动范围、兼容、资源清理、隐含副作用和维护成本，而不只核对功能。
- 固定候选身份：有授权可提交Git；没有则以明确基线和文件/补丁身份交接，不擅自提交。
- **产出**：准确候选身份 + 变更摘要 + 测试结果 + 已知限制。

### 4. 独立审查：功能正确性、需求一致性与三个方针

审查者阅读有效需求和候选代码，自主追踪关键链路，必要时执行隔离验证。主要范围固定为：

**R3任务可采用双独审分工**：

- 独审A：功能正确性 + 需求一致性。
- 独审B：三个产品方针。

两位审查者均独立于实现者，基于同一有效需求和同一固定候选开展审查，各自形成结论。主控汇总两路意见，确保总体覆盖完整；任一路有阻断项均需处理，不能用另一路通过抵消。双独审是可选的职责拆分，不改写既有风险验证、权限和验收闸门。

| 维度 | 重点问题 |
|---|---|
| 功能正确性 | 正常、边界、失败及恢复路径是否正确；回归是否有效；证据是否对应候选；测试通过是否掩盖实际错误 |
| 需求一致性 | 是否实现目标、遗漏要求、违反非目标或未经授权扩张职责；有无用复杂机制替代必要的需求澄清 |
| 方针一：降低使用者心智负担 | 是否增加必须学习、配置、审批或理解内部机制的步骤；恢复操作是否简单明确 |
| 方针二：开箱即用、自动降级 | 是否新增DSH之外的使用者依赖；缺能力时能否继续使用，并如实轻量标记降级状态 |
| 方针三：变更安全性与长期可维护性 | 职责、状态和副作用边界是否清晰；是否增加隐藏调用顺序、跨层复制政策或不必要机制；后续普通变更是否更容易做对 |

- 三个方针以 [现行原文](<../PRODUCT-PRINCIPLES.md>) 为准，同时遵守其安全、审计和数据底线。使用者零负担不代表开发者可以省略验证和回滚。
- 每项问题区分事实、触发条件、后果和确定程度；明确必须修复项与非阻断项，避免把个人风格偏好扩成新需求。
- **产出**：可追溯的审查结论及覆盖范围，不以“看起来可以”代替依据。

### 5. 集成与交付：默认推进到合入并验证合入结果

- 按有效授权把通过审查的候选合入约定目标分支，不在“子代理完成”或“候选已审”处例行停止；若确实缺少所需权限，说明例外，任务仍不算默认完成。
- 合入前再次核对目标分支水位。若基线已前移或仍需冲突处理，返回自己的开发分支/worktree同步、解决、复验，并对受影响增量复审；不得在基线工作树现场解决冲突或修改已审候选。
- 目标基线只接收已经整合、验证和审查的结果，不承担冲突解决、研发调试或失败试错。合入操作不能顺带产生未经验证的新代码。
- 记录最终合入身份和验证结果，核对需求及审查结论仍适用于最终产物。
- 发布、部署、重启不属于默认合入终点。任务另有运行生效授权与要求时，核对准确目标及实际运行版本，不以另开服务代替目标更新。
- **产出**：最终合入身份、集成验证、未执行的发布/部署环节及必要回退方式。

### 6. 验收关闭：按本卡真正的终点判完成

- 最终证据对应本卡最终产物；提交任务只进入review，不自动等于完成。
- 由具备权限的验收者按任务规则裁决；候选审查若已覆盖最终产物，可复用，不机械再做一轮全量审查。
- 审查后新增修改，只补审受影响范围和新风险；不能拿旧版本通过结论覆盖新修改。
- 默认在合入且最终结果验证、验收条件达成后才verify/done；例外按卡片约定，不能用待合入候选替代。单列未部署、未人工体验、未覆盖支持环境等事实。
- 多任务卡场景由主控在当前卡结清后接续下一张获准且满足依赖的任务，保留简洁进度记录，不为普通阶段转换追加用户确认。
- **产出**：简洁完成说明：改了什么、证据、合入位置、剩余事项、用户是否需要操作。

## 4. 退回、恢复与升级

| 发生什么 | 回到哪里 / 怎么处理 |
|---|---|
| 局部实现或回归失败 | 回实现、自验，不找用户代判普通技术问题 |
| 独立审查发现阻断项 | 退回修复，更新候选身份，再针对变更复审 |
| 合入前基线前移、出现冲突或候选需调整 | 回自己的开发分支/worktree同步与处理，再复验、按影响复审；不在基线上解冲突，不套用旧结论 |
| 需求冲突、扩大产品责任、缺少关键权限 | 向用户说明具体问题与选项，获确认后更新有效基线 |
| 长任务中断、租约轻度过期或会话切换 | 对账任务、工作区和实际副作用后恢复；不盲目重跑非幂等操作 |
| 发现无关问题 | 单独登记与判断优先级，不无限扩张当前任务 |

需要恢复时，区分已提交、确定未提交、结果不确定；保留已有工作与证据，不把失去回执当成没有执行。

## 5. 最小交接包

尽量放在现有任务和方案中，不要求每步新增报告：

1. 有效需求/方案与授权边界。
2. 基线、候选/最终产物身份及变更范围。
3. 验证结果、失败归因和未覆盖项。
4. 独立审查结论及后续修改是否已复核。
5. 当前任务状态、运行生效情况、下一步与必要用户动作。

## 6. 后续可细化的事项

- **审查深度**：在既定审查范围与R3可选双独审分工下，局部任务的粗审和高风险专项深审怎样安排？
- **验证范围**：定向、默认、全量、宿主/运行检查如何分级？
- **执行细则**：模型选择、并行冲突控制、候选与合入版本的交接、权限例外如何记录？

完成终点、实施分工、超过3个代码文件的默认worktree隔离及R3可选双独审按正文执行。具体工具命令、文件模板和分支策略在任务授权与现行约束内选择；本文不授权新增流程引擎或自行启动未获准任务。
