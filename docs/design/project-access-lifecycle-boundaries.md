# 实施方案：项目读取、业务准入与 writer 生命周期分离

> 状态：待实施（本篇为方案/规格，不构成能力已交付声明）。

状态：已批准的实施方案。整体实施、回归和独立验收待执行。现行行为见实现契约。

目标：治理 `open` 职责耦合导致的变更安全性缺陷，而不是仅更名、移动代码或要求调用方记住更多顺序。优先级依据 [产品方针三](<../governance/PRODUCT-PRINCIPLES.md#方针三变更安全性与长期可维护性是一等工程质量属性>)，不以生产事故为前提。

## 1. 问题与范围

[service.open](<../../lib/core/service.js#L182-L209>) 实际是 operational 项目句柄获取：缓存复用，或加载存储、取得写锁、修尾、修元数据、恢复任务。它服务读写两类入口及宿主生命周期，不是纯查询函数。

当前宿主必须在调用它之前理解并镜像部分核心准入顺序，见 [HTTP](<../../lib/host/routes.js#L53-L81>) 与 [文档工具](<../../lib/host/tools/doc.js#L128-L150>)。这是需要治理的边界，而不是“open 这个名字不够清楚”。

方案覆盖：读取能力、核心准入、按需 writer 获取/恢复、调用方迁移与失败发布。保留事件日志、状态机、单写者与恢复规则；不引入数据库、通用事务框架或持久化第二套读库，不顺带重做所有业务命令。

## 2. 方向选择

| 方向 | 优点 | 代价/问题 |
|---|---|---|
| A：只在显式写入时准备 writer | 边界最小，不恢复未使用项目 | 无活跃写入时恢复推迟；首次写入可能因恢复推进 rev 而冲突 |
| B：活跃会话生命周期按需准备，写入口统一兜底（推荐） | 活跃项目提前准备；查询不承担恢复；新项目/迟加入仍可正确写入 | 需要管理按项目准备中的状态、失败和关闭，不能只挪到插件加载函数 |
| C：独立恢复服务与持久读库 | 隔离充分 | 多投影同步、重建和部署成本，不作为本轮默认方案 |

采用已批准的 B 方向。插件加载只扫描与处理当前活跃会话，不全量打开所有历史项目；活跃 agent 挂接及真正的写操作共用一个 core 内部 writer 获取机制。按项目 single-flight 和现有服务生命周期实现，不另造通用调度框架。

只把 recover 挪进 apply 不够：项目可在加载后出现、没有 agent、发生准备失败，或被另一进程占用，仍需要明确处理。

## 3. 三种能力，不再用一个 handle 承担

| 能力 | 允许 | 禁止 |
|---|---|---|
| 纯派生 | 从传入快照与 now 计算 DTO | 获取数据、读系统时钟、写状态 |
| 只读项目访问 | 读取/校验日志与快照、读取文档；内存缓存 | 创建目录/项目、writer 锁/心跳、修尾、heal、recover、隐式续租 |
| operational writer | 显式准备/恢复，执行命令、会话生命周期操作 | 以普通查询返回对象的形式泄漏给调用方 |

读取允许 I/O，并非“没有任何计算或缓存”；要求的是不改变项目持久状态、运行时租约或工作区文件。操作系统读取元数据变化不属于业务写入承诺。

建议的服务接口形状（名称待实现前确认）：

```js
service.resolve(ref)                    // 只定位，不创建
service.read(ref, view, args)           // 只读派生，返回脱离 live 对象的 DTO
service.execute(ref, command)          // 内部统一准入、准备、执行，不让 host 编排
service.create(input)                  // 明确创建；复用既有项目只返回描述信息
```

`acquireWriter`、恢复及共享引用管理留在 core 内部。维护 apply 可使用明确标识 operational 的入口，但不得通过普通读取返回 command/store/service/attach 等能力。

不提供 `read({ recover: true })` 或到处传 `readonly` 布尔值的混合模式；只读失败也绝不 fallback 到旧 open。

## 4. 读取如何取得正确数据

### 已有同进程 ready writer

捕获同一次已提交的 state/rev/hash，以及所需 bindings、leases 的副本和 now；查询只消费快照，不持有可写 handle。输出必须脱离 live 嵌套引用，避免当前 [taskView](<../../lib/core/views.js#L100-L123>) 等路径的别名泄漏。优先投影必要字段后脱离输出，不把每轮全项目深复制当作默认性能方案。

### 冷项目与其他进程持有 writer

只读回放持久状态，不生成 live lease。响应区分“持久化事实”和“当前运行态未知”：保留日志中的 in_progress，不擅自改成 ready；无本地 lease 不等于任务无人占用。运行态相关 allowedOps 是提示，不能伪装为已获执行授权。

每次读检查磁盘指纹；变化时重新验证读取，发布前复核。替换/截短全量重读；完整校验失败、版本不支持或竞争超过有界重试时明确报错，不吞成“不存在”，也不进行修复。现有 [MCP 只读入口](<../../lib/core/project-reader.js>) 和 [无锁回放](<../../lib/core/store.js#L434-L442>) 已覆盖限定读取场景。实施时逐项核对读取入口、错误语义和运行态信息，再决定可复用的边界。

快照只承诺“某个已验证提交水位”，不宣称跨进程线性一致。缓存必须区分来源、seq/hash和运行态有效性，不能仅靠项目 rev 判断租约、外部文件或其他进程是否变化。现有列表/health 的 worker 限流和生命周期保护继续保留；不把全量冷回放重新塞回宿主热路径。

这不是另一个查询表达式引擎。[查询 v2 契约](<../decisions/query-v2-first-task-contract.md#沿用的接口>) 的 QuerySource 及“不自行取数/回放”边界保持不变，项目读取层只负责提供对应数据。

## 5. 业务拒绝由 core 保证顺序，不由 host 猜

HTTP/工具只负责身份来源、传输信封、路由参数和命令映射。core 为每个操作集中维护一份纯参数归一化与准入规则，由内部执行入口和需要的 dry-run 共同使用。不要另造一套“差不多”的校验，也不要让 host 手工调用 prepare 再决定何时 open。

执行顺序：

```text
归一化与静态准入
  → 只读定位/快照
  → 可提前判定的核心政策/权限检查
  → 按需取得 writer
  → 基于最新数据重验准入
  → 必要恢复
  → 串行执行前重验 rev、租约、时间与业务条件
  → 提交事件
```

- 先从 inline put/link 与外置写等已有拒绝保证的操作落地；随后逐操作迁移，保留其既有错误顺序，不能机械套同一串检查。
- 归一化只做一次，复验复用同一核心函数。若内部保留预备结果，其身份需绑定规范化命令、项目、提交水位、相关 registry/能力上下文和服务 generation；不把它当授权，也不只按 rev 跳过时间/租约检查。
- 不使用现有 [_preflight](<../../lib/core/handle.js#L270-L294>) 来实现纯准入：它执行同一 handler，可能预写 blob 或 registry。
- 不把失败读取当“不存在”后自动创建。允许创建的命令必须在虚拟初始状态/默认策略上先通过可提前判定的准入，再显式 genesis；不宣称 genesis 与第一条业务命令跨文件原子。
- 不替用户修改 expectedRev。恢复或并发修改使其过期时，明确返回最新水位和重读指引，不自动重放非幂等业务。

### “拒绝零写”的承诺边界

保证：**本请求进入 writer 获取前已可判定的 malformed、政策禁写、静态角色拒绝、不存在且不允许创建等拒绝，不触发持久写、创建或续租。** inline 默认禁写这类静态政策必须由 core 拦在 writer 前。

不能笼统保证所有 400/409 零写：取得锁本身可能写锁文件；并发变化后的复验拒绝，或恢复推进 rev 后的 CAS 拒绝，可能已有生命周期写入。实施时按现有各操作契约逐条确认，不能借本方案悄悄缩减已承诺保证，也不能在注释里继续写“所有 400 都零写”。

后台独立生命周期写与请求引起的写分别记因果；测试在受控无后台活动的 fixture 中比较副作用，不能因外部心跳恰好发生就混淆责任。

## 6. writer 准备与发布必须成功后生效

准备状态至少区分 preparing、ready、失败；同一 canonical 项目目录只允许一个准备 flight。

- preparing 与 ready 共享表分开。加载、必要恢复成功后才发布本地缓存/SHARED_HANDLES、计入可用引用；调用方不能取得半初始化 handle。
- [recover](<../../lib/core/handle.js#L323-L334>) 的完成标记应在恢复提交成功或确实无需事件后置位，而不是提交前。
- 准备失败只撤回自己的 candidate/flight，关闭 store、心跳与关联资源，释放自己持有的锁和 OPEN_STORES 记录；不驱逐其他 service 的 ready writer。
- 确定回滚后可由下一次明确需求重试；不确定写继续 fail-closed，重新校验 durable 日志后才能恢复，禁止盲目重复提交。
- 锁忙就不取得 writer；只读读取仍可继续。不把 readonly follower 当作 ready writer 缓存。
- 保留引用计数、单写者、hash/seq/幂等索引、归档保护，以及租约终止和任务迁移同 commit 的恢复规则；共享上下文不得错误继承更高特权。
- 关闭时封闭新入口、使 pending generation 失效，明确排空/拒绝已排队工作，再释放最后引用。旧 service 关闭不能杀死新 owner 正在使用的 writer。

attach/detach 的真实 lease 变更必须与成功提交点一致，不能在新生命周期入口继续保留“先删 live lease 再 append”的失败窗口。它与失败初始化发布同属本方案必须检查的生命周期边界，但不要求本轮重写普通 command 工作副本机制。

## 7. 调用方迁移

| 调用方 | 目标职责 |
|---|---|
| HTTP board/task/plans/docs/events/summary | read；先匹配资源，未知路由不取得 writer |
| HTTP health | 从只读快照提交现有独立审计；保留 fresh/过时/超时保护 |
| HTTP commands 与外置写操作 | execute，由 core 管顺序 |
| POST external fixed、工具 get_fixed | 仍是只读；按操作语义分流，不按 HTTP 方法粗分 |
| 读工具 get/list/board/inspect | read；inspect 的文件/Git观察是只读能力，不带恢复/confirm |
| 写工具 task/plan/doc/session | execute；允许创建的入口显式声明创建语义 |
| agent 加载/创建/恢复、解绑 | 显式生命周期操作，按需准备、恢复/绑定或释放；与命令共享串行边界 |
| Prompt callback | 仅读已捕获内存数据，不加载、不触发准备、不续租 |
| create(existing)、工作树复用 | 定位描述信息，不因“确认已存在”自动恢复 |
| import/relocate/bind | 无副作用检查与真正 apply 分段；写锁内重验身份 |
| 运维 dry-run/inventory | snapshot/纯计划；不能先 operational open 再判断 dry-run |
| 运维 apply | 授权、备份、停写门禁通过后明确取得 operational 能力 |
| 副本回放、容量和故障夹具 | 默认只读验证；确需恢复/写入的合成实验明确申请 operational 能力 |

## 8. 租约与恢复：生命周期负责，保持简单

[现行契约](<../CONTRACT.md#26-plan--task-规则>) 规定 DSH 看板工具调用尝试 touch；[touch](<../../lib/core/handle.js#L369-L385>) 更新活性/租期，也可能触碰锁心跳。实施应同步调整这项复合语义，让查询不承担活性管理；不能只把 touch 延迟到后台就宣称消除了查询副作用。

已批准的约束：

1. TTL采用15分钟的时间尺度。代码默认已经是900秒，另有900秒宽限和两次无进展续租限制；本方案不是单纯增大TTL数值，也不是直接删除全部租约限制。
2. 续期及活性维护归生命周期owner，优先复用必要的现有宿主活动信号。不得为实时判断新建高频探测、独立心跳协议或复杂调度，不要求使用者频繁手工renew。
3. 区分“租期/静默窗口”与“任务总耗时”，以及“看板没有新进展”与“宿主已停止执行”。无进展上限的处理不能冒充活跃源确已丢失；不能仅靠延长TTL声称长任务永不过期。
4. 恢复路径通畅优先。轻度时间过期、同一session/epoch持有效token、且未被其他owner接管时，提供简单续接，不增加多轮手工恢复流程。
5. 明确解绑、代际变化、已撤销或已重新授予等所有权失效，保留必要的恢复确认与fencing保护；lastSeen过旧只是超时推断，不是宿主停止的确证。
6. 不让已失效旧token复活，不覆盖新owner，不自动重放或猜测已经发生的外部副作用。简化的是恢复操作，不是所有权与证据安全边界。

实施先以最小合成案例确认可用宿主信号与续接路径，并明确宽限、无进展限制与生命周期更新的关系。若现有宿主能力不足，须报告这一具体设计例外，不得自行新增复杂机制或以增加用户手工操作兜底。外部工具语义和现行契约在实现中一起更新，不能只改内部命名。

不新增使用者配置或审批步骤，也不承诺实时知道进程失活。允许轻度过期，只要保留安全、简短、可重试的恢复路径。

## 9. 分期与验收

1. **固定边界及失败发布**：确认副作用矩阵；补准备失败不发布、恢复完成标记和资源清理的故障回归。此阶段不宣称所有读取已安全。
2. **引入只读能力并迁移读取**：实现快照/错误/freshness及DTO隔离，迁移HTTP与读工具；读工具活性维护按第8节归生命周期owner。只读路径禁止引用 operational 获取入口。
3. **统一核心准入与生命周期**：先覆盖已有“拒绝零写”的操作，再逐项迁移写入口；agent准备、迟加入、reload与关闭复用同一owner机制。
4. **迁移维护脚本并收口旧入口**：dry-run/apply分开；旧open若短期保留，只能是明确operational兼容壳，普通host路径不得引用，给出移除范围。同步契约、架构图与runbook。

实施时验证矩阵：

| 场景 | 必须验证 |
|---|---|
| 冷/热/空root/缺项目/readonly下读取与dry-run | 不创建项目/目录/锁/心跳，不修复日志/元数据，不改变租约；读取失败不fallback writer |
| malformed、数字标题、坏links、默认禁写、已迁移档案 | HTTP/工具/core使用同一归一化与准入，保持错误顺序；可提前判定的拒绝零写 |
| writer准备时并发政策/registry变化、恢复推进rev | 重验，不使用陈旧批准，不改expectedRev，不声称所有冲突零写 |
| recover EIO/ENOSPC、uncertain | 不发布失败句柄；清自身资源；确定回滚可重试，uncertain按durable事实恢复，事件不重复 |
| 两进程、日志替换/截短/半尾/完整无LF/损坏版本 | 明确水位与错误；只读绝不修尾，writer保留既有恢复保障 |
| 双service/reload/迟加入/关闭排队/attach-detach失败 | 引用计数和准备single-flight正确，无半初始化发布、真实lease提前丢失或closed后预写 |
| DTO/快照/运行时未知 | 不泄漏可写handle/live Map/嵌套别名，不把无本地lease当无人占用，不假装已恢复 |
| 代表性后续业务变更 | 增加入口或撤销能力不需host复制政策、不需理解恢复顺序；自动回归能拒绝错误组合 |

以上是拟执行验证，不是已通过结果。成本/时延不编造数值；保留现有worker隔离与明确的错误、过时、取消边界。

## 10. 批准范围与非目标

用户已批准按本文定稿建卡：采用B方向、副作用归生命周期、纯读取与核心准入分离，租约按第8节保持简单并保证恢复通畅。接口命名、冷快照运行态提示形状和内部准备状态在实施节点最小确认，不再派生一组可选模式；旧open不新增普通host调用，本卡内迁移普通读写入口，必要维护兼容入口必须明确operational语义与使用范围。

不包含：SQLite替换、日志schema迁移、全量启动恢复、通用事务/调度框架、command临时状态替换的整体重写、全库深clone、浏览器交互重做。项目摘要字面文本按[独立方案](<prompt-literal-section.md>)处理。

方案验收须核对实现、回归和独立审查结果。发布与真实宿主更新按届时授权处理。
