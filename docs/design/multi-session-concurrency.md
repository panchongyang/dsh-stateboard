## 1. 已确认的实现基础

- 单项目的命令提交经串行命令总线进入日志，串行区间不覆盖任务后续的整个开发过程；保留单写者并不妨碍多 worker 并行执行不同任务。见[命令总线](<../../lib/core/handle.js#L118-L196>)。
- 默认项目 WIP 为 2、每个 agent 会话为 1，具体值可由项目 policy 覆盖；claim 检查任务状态、依赖、租约与配额。见[默认策略](<../../lib/core/normalize.js#L8-L19>)、[领取检查](<../../lib/core/commands/task-work.js#L14-L28>)。
- 多计划各有版本 CAS；focus 不构成执行许可，阶段顺序不构成隐式依赖。
- active revise 对复用任务及移除成员均触碰任务 rev，且这条路径没有与普通任务编辑等价的执行期保护；这是编排与执行相互干扰的主要位置。见[修订任务事件](<../../lib/core/commands/plan-life.js#L301-L346>)。
- adopt 的跨计划归属保护与 revise 的 taskId 校验不一致；跨计划依赖已有可达入口，但 revise 只验局部 key 子图；归档只扫描当前版本成员。见[成员操作](<../../lib/core/commands/plan-members.js#L29-L96>)、[修订入口及依赖](<../../lib/core/commands/plan-life.js#L242-L277>)、[归档检查](<../../lib/core/commands/plan-life.js#L362-L384>)。

正式实施前须在冻结候选基线上重新核对这些落点，不能把文档行号当作运行实例已经加载该版本的证明。

## 2. 目标模型与不变量

1. Project 是全局任务依赖图、总配额与审计边界；Plan 是交付目标，Step 是分组，Task 是唯一有租约、intent、提交与验收的执行单元。不引入父子任务或计划级执行租约。
2. 同一计划与不同计划中的独立任务都可并行。一个 agent 会话默认执行一个任务，协调者不因管理计划而占有全部任务。
3. taskId 稳定。任务最多有一个当前主归属，也可处于计划外；其他计划可依赖或关联该 taskId，不能复制一份执行权。历史计划快照引用同一任务不等于存在多个当前归属。
4. 区分当前成员关系、历史计划版本出处与本次执行采用的定义版本。不能要求所有 worker 的 planRef.version 永远追随最新计划版本。
5. 阶段仅分组；确需阶段屏障时落成显式任务依赖或验收门。focus 保留人的关注语义，worker 的候选计划范围是另一项显式配置。
6. 任务依赖属于完整项目 DAG，可跨计划。所有修改依赖的入口共用完整图验环与 readiness 计算；前置任务 review/canceled/archived 不被偷偷当作 done，候选应解释不可执行原因。

## 3. 解耦编排、定义与执行

概念上分为 PlanVersion、TaskDefinition 和 TaskRun。首期可以保留现有物理存储，采用最小附加字段及统一校验，不以大规模拆表为前提。

| 变更 | 目标规则 |
|---|---|
| 计划目标、阶段标题、展示顺序 | 仅改变计划结构版本，不更新未变化任务的执行 rev |
| 非执行中任务的依赖、验收与工作范围 | 检查被修改任务 CAS、状态与完整项目 DAG，再原子提交 |
| 执行中任务的工作契约 | 首期拒绝修改；先停止、结清 intent，再开启新定义/attempt，不静默重解释已完成工作 |
| 计划归属或阶段移动 | revise/adopt/release 共用校验；执行中拒绝；跨计划转移显式操作并原子校验双方版本与任务版本 |
| 从当前计划移除 | 明确当前归属与历史出处；任务、证据与审计不删除，不产生含混双归属 |
| 归档 | 对完整归属/执行集合检查活动任务、orphan、有效租约和 open intent；首期拒绝存在未结清执行的归档 |

任务定义、运行状态及成员关系分别需要哪些 revision 字段，由第一项契约任务冻结；不得只换字段名而继续全量触碰所有任务。针对无变化任务的计划修订，worker 应能继续使用自己的有效任务版本和执行契约。

所有真正修改任务的入口必须复用任务保护，不能用 plan baseVersion 替代 task expectedRev，也不能以协调者角色绕过 lease/fencing、人审和证据约束。

## 4. 调度与原子领工

拟新增 `claimNext(planIds?, capabilities?, cmdId)`，在同一权威写者事务内：筛选可 claim 候选 → 检查项目/可选计划/会话/资源预算 → 按优先级与计划公平性选取 → 发放租约/token → 记录可恢复的选择结果。

- 选择与 claim 不拆为两个客户端步骤；无候选返回可解释的空结果，不能反复抢排行榜首项。
- 人工指定 taskId 的 claim 仍有效，并与自动领工共用所有保护。
- 全部执行入口（包括 reject/reconcile 后重入执行）必须使用一致的配额及资源规则，不能只保护 claimNext。
- cmdId 重试不得产生第二个任务；响应丢失后应能查回选中任务及结果，并重新核对租约有效性，不复活过期执行权。
- 普通任务命令采用局部 CAS，避免附带不必要的全项目 expectedRev。stale-revision 重读后判断语义；fencing-stale/lease 丢失须停止并 reconcile，不能读取新 token 后冒充新 owner。
- 并发执行开关仅在任务隔离、执行绑定及证据路径准备完成后启用；本计划不自动提高当前项目配额。

## 5. 兼容、故障与范围

必须保持 cmdId、单调 token、session/epoch、intent 结算、证据强度、人审开关及原子拒绝无副作用等既有保证。新增事件/投影/凭证字段须有版本兼容、旧日志重放、重启及恢复规则，不修改历史日志。归属迁移和新定义版本的缺省含义必须在契约任务中明确。

权威服务重启后沿用现有回收/reconcile 原则；磁盘上的 worktree 不代表还有执行权。不得凭旧 PID、目录或分支存在就恢复 owner、强杀进程或自动清理成果。

首期非目标：文件日志多写者、数据库迁移、跨主机自动接管、全自动无人值守推进、自动合入/部署、把 worktree 当 OS 沙箱、浏览器自动探针。多进程 worker 可在后续通过鉴权 API/RPC 使用同一权威写者；不能各自绕开文件锁。
